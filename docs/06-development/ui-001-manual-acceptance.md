# UI-001 — ручная приёмка ежедневной фиксации веса

## Предусловия

- изолированная test-server topology использует verification commit ветки `ui/ui-001-daily-weight`;
- web, API, PostgreSQL и Redis healthy, актуальные migrations уже применены;
- создан совершеннолетний test user с `onboarding_status=completed`, тестовым token balance и несколькими weight entries;
- browser API доступен только через same-origin `/api/v1`, а API, worker, PostgreSQL и Redis не публикуют host ports;
- проверка выполняется в mobile viewport и на desktop.

## Основной сценарий

1. Открыть `/login`, ввести тестовые email и пароль и проверить disabled-кнопку `Входим…` во время запроса.
2. Убедиться, что completed user перенаправлен на `/today`.
3. Проверить сегодняшнюю дату, последний вес, нейтральное изменение и недавнюю историю.
4. Ввести вес с запятой, например `98,45`, и нажать `Сохранить вес`.
5. Во время запроса проверить disabled-кнопку `Сохраняем…`.
6. После ответа проверить спокойное подтверждение `Записано`, новый последний вес и новую строку истории.
7. Обновить страницу и убедиться, что запись загружена из существующего weight API.
8. Проверить график над списком: точки идут в хронологическом порядке, а одна запись и несколько записей за день не ломают шкалу.
9. Открыть `Поговорить с AI` и нижнюю вкладку `AI`; убедиться, что `/quick-reply` показывает persisted ленту сообщений, а вкладка `Сегодня` возвращает на `/today`.
10. Отправить два разных сообщения подряд: каждое появляется в ленте, во время fake AI operation показано ожидание, после polling появляется сохранённый ответ.

## Негативные сценарии

1. Ввести `98,456`: UI должен показать validation error и не отправить POST.
2. Проверить допустимые варианты `98`, `98,4` и `98,45`: каждый должен сохраняться без потери точности.
3. Прервать сеть на первом POST, затем восстановить её и нажать `Повторить сохранение`: должен повторно использоваться тот же `Idempotency-Key`, а в истории должна остаться одна запись.
4. Прервать сеть до загрузки страницы: показать спокойную ошибку и рабочую кнопку `Попробовать снова`.
5. Ввести неверный пароль на `/login`: показать понятную ошибку без раскрытия существования аккаунта.
6. Очистить/просрочить session cookie: `/today` должен перенаправить на `/login` без отображения персональных данных.
7. Проверить пользователя без записей: показать `Здесь появятся ваши изменения. Начните с сегодняшнего веса.`
8. Потерять ответ первого AI POST и повторить отправку: используется тот же `Idempotency-Key`, создаётся одна operation и списывается один токен.
9. Отправить другой текст: используется новый `Idempotency-Key`, а `Unexpected server error` не появляется.

## Definition of Done applicability

- Код и web tests: применимо.
- Миграции: применимо для UI-002 — migration `0006_ui_002_weight_precision.sql` переводит numeric precision без потери существующих строк.
- API documentation/contracts: применимо — DTO/OpenAPI допускают вес до двух знаков и owner-scoped чтение persisted AI conversation/messages.
- Analytics events: N/A — новые frontend events не создаются; `weight_added` уже возникает на backend.
- Ownership: применимо и проверяется server-side для weight entries, AI conversations, messages и operations.
- Test server: применимо; отдельный Compose project `atlas-ui-001` публикует только gateway/web port, заданный `UI001_PUBLIC_PORT` (по умолчанию `3102`).

## Результат 2026-07-22

- Основной browser-сценарий выполнен Chromium mobile против реального API: completion, empty state, save `98,4`, `Записано`, reload persistence и переход в AI.
- Component tests подтверждают latest/history, validation, loading/error/retry, session expired, disabled state и стабильный ключ сетевого повтора.
- Визуально проверен mobile viewport: главное действие, summary и история читаемы; AI остаётся вторичным действием.

## Результат UI-002 2026-07-23

- В isolated `atlas-ui-001` migration `0006` применена дважды; `weight_kg` имеет `numeric(5,2)`, а существующие записи сохранены.
- Browser/mobile acceptance подтвердил сохранение и отображение `98`, `98,4` и `98,45`.
- `98,456` получает понятную client-side ошибку и API возвращает `422 VALIDATION_ERROR`; identical retry с тем же `Idempotency-Key` не создаёт вторую entry.
